### Highest-risk discrepancies and assumptions

1. The inspected service folder is a local snapshot with no commit/version proof for the current target. **No candidate route is promoted to a live contract** until the owner identifies the exact running build/contract version and safe test base.
2. The UI's mobile/provider/RPA-plan resource fields and seven KPI meanings are not represented by the examined VPS DTO/map summary. Joining or fabricating counts would be misleading.
3. The UI bulk XLSX is not accepted by the examined service's exact-header import parser; `confirm=true` is a real multi-row DB write without an observed idempotency key.
4. RDP test writes status and tests only TCP; `AVAILABLE` vs an older UI's `ONLINE` is a concrete source mismatch. Real launch involves a short-lived token and native helper, not browser-only auto-login.
5. Zero-Touch readiness requires real manifest/component gates. Preview Package/Ready states cannot be carried into integration acceptance.
6. `GET /api/v1/workers` refreshes offline states and commits. Treating every GET as read-only for a safe test would be wrong.
7. Resource deletion/cleanup may cascade or be blocked by active dependencies. A recoverable UI preview removal is not a service rollback strategy.
